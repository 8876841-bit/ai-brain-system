# Codex 工作说明

## 1. 项目定位

这个仓库是我的个人认知系统仓库。

它不是资料库，不是案例库，不是日记库，也不是内容素材库。

它的目标是把我日常接触到的零散信息，转化为可以长期复用的认知资产，包括：

- 问题
- 洞察
- 方法
- 技能
- 模型
- 行动判断

核心目标：

> 把零散输入转化为可复用的认知系统。

---

## 2. 当前背景

用户是一个工作繁忙、信息敏感、想法很多的人。

用户会在以下场景中产生零散记录：

- 看播客
- 刷视频
- 看文章
- 研究人物
- 学 AI
- 做内容
- 想商业机会
- 观察自媒体与时代变化

记录形式可能包括：

- 手写笔记照片
- 截图
- 手机备忘录
- 零碎文字
- 语音转文字
- 一个人名
- 一个陌生概念
- 一个突然冒出来的问题

用户的问题不是没有输入，而是输入过于分散，导致后续无法稳定整理、消化、内化和转化。

## 3. 工作原则

### 3.1 GitHub 的角色

GitHub 不是用户每天手动编辑的入口。

GitHub 只作为最终沉淀仓库。

用户的日常输入入口应该是 ChatGPT 对话框。

正确流程：

```text
用户输入碎片
↓
AI 识别、分类、追问、整理
↓
用户用一句话校正
↓
AI 生成或更新 Markdown 文件
↓
GitHub 保存最终沉淀结果
```

### 3.2 用户的角色

用户只负责：

- 捕捉信息
- 发图片 / 截图 / 文字 / 语音转文字
- 简单说明当时为什么记录
- 对 AI 整理结果做最小校正

用户不应该长期承担 Markdown 文件维护工作。

### 3.3 AI 的角色

AI 负责：

- 原始识别
- 判断真实意图
- 分类
- 提炼问题
- 提炼洞察
- 判断是否值得深挖
- 判断是否可以升级成模型
- 生成可入库 Markdown
- 必要时更新 GitHub 文件

---

## 4. 仓库边界

本仓库只放认知系统和方法论。

可以放：

- 概念理解
- 人物路径研究框架
- 问题沉淀
- 洞察
- 灵感
- 技能路径
- 行动规则
- 认知模型
- 系统工作流

不适合放：

- 单个视频的完整复盘
- 单个平台账号数据
- 具体内容案例库
- 客户项目材料
- 业务文件
- 合同
- 具体素材

具体内容案例应另建仓库，例如：

```text
content-case-library
xiaohongshu-content-cases
```

本仓库负责沉淀模型；案例仓库负责验证模型。

## 6. 分类规则

### 6.1 输入层

#### Concept 概念

用于存放用户不理解但想弄明白的词、术语、机制。

例子：

- 幻方
- token
- Agent
- workflow
- 非线性选择

#### Person 人物

用于存放用户想研究的人物。

重点不是八卦，而是路径研究：

- 这个人是谁
- 成长背景是什么
- 为什么能做出结果
- 关键转折点是什么
- 能力结构是什么
- 哪些路径可以迁移，哪些不可复制

#### Case 案例索引

只放案例索引或案例摘要，不放完整实战材料。

---

### 6.2 思考层

#### Question 问题

用于存放尚未解决、需要进一步研究的问题。

例子：

- 什么是高密度环境？
- 怎么把模型能力转译成人能理解的内容？
- 如何把复杂的东西讲清楚？

#### Insight 洞察

用于存放用户已经产生初步判断的内容。

特点：

- 不是纯信息
- 已经有用户自己的判断
- 但还不一定成熟到可以成为模型

#### Idea 灵感

用于存放可能变成选题、项目、内容、产品或副业方向的想法。

---

### 6.3 行动层

#### Skill 技能

用于存放用户想掌握的能力。

例子：

- AI 自动化
- Agent 搭建
- 内容转译能力
- 复杂表达能力

#### Action 行动

用于存放行动规则、复盘方法、执行计划。

---

### 6.4 系统层

#### Model 模型

只有当一个结构经过多个案例或多个场景验证后，才进入 Model。

模型必须能反向指导下一次行动。

模型不是漂亮总结，而是可复用判断工具。

---

## 7. 当前已出现的重要主题

### 7.1 认知路径模型

用户通过外部信息触发兴趣，然后尝试从人物、概念、技术和时代变化中提取自己的机会路径。

结构：

```text
触发 Trigger
↓
探索 Exploration
↓
模式识别 Pattern
↓
能力提取 Capability
↓
方法追问 Method
↓
核心问题 Deep Questions
↓
自我定位 Positioning
```

### 7.2 复杂表达模型

用于帮助用户理解如何把复杂问题讲清楚。

核心顺序：

1. 先说明为什么讲
2. 先给总框架
3. 每个术语都要转译
4. 用类比降低理解成本
5. 按流程讲
6. 每一段都回答“所以呢”
7. 最后总结成一句话

### 7.3 空间讲解模型

用于家装、建材、柜体、空间内容表达。

核心公式：

```text
用户痛点 → 设计动作 → 体感结果 → 适用条件 → 判断标准
```

注意：

空间好不好，不从“设计点”开始讲，而从“用户动作”和“用户决策”开始讲。

## 8. 处理一批笔记的标准流程

当用户发来一批笔记时，不要马上建很多文件。

先做以下处理：

### Step 1：原始识别

识别用户发来的图片、截图、文字中有哪些内容。

如果不确定，必须标注“不确定”。

不要把不确定内容强行整理成确定结论。

### Step 2：意图判断

判断用户为什么记录它。

重点回答：

```text
用户是被什么东西勾住的？
用户真正想解决的不是字面问题，而是什么？
```

### Step 3：分类建议

把内容归入：

- Concept
- Person
- Case
- Question
- Insight
- Idea
- Skill
- Action
- Model

### Step 4：深挖判断

判断这条内容应该：

- 暂存
- 查资料
- 做人物卡
- 变成问题卡
- 找案例
- 做实验
- 升级成模型

### Step 5：等待用户校正

用户只需要用短句校正。

例子：

- 这个分类对
- 这个词识别错了
- 这里不是内容方向，是高密度环境
- 这个问题我想优先研究

### Step 6：入库

用户确认后，再生成或更新 Markdown 文件。

## 9. 用户偏好的协作方式

用户不希望每天手动维护 GitHub。

用户希望：

- 低摩擦输入
- AI 自动识别分类
- AI 生成结构化内容
- 用户只做最小校正
- GitHub 自动或半自动保存最终结果

因此，后续工作应避免让用户反复：

- 手动建文件
- 手动复制大段文字
- 手动整理 Markdown
- 手动移动分类

除非 GitHub 权限不可用，否则应尽量由 AI 完成入库动作。

## 10. 常用短命令

用户可以使用以下短命令：

### 只识别

只识别原始内容，不分类、不分析。

### 分类入库

识别 + 分类 + 生成可入库 Markdown。

### 深挖这个

对某一个问题进行定义、语境、案例、验证、和自己的关系分析。

### 升级成模型

当一个主题已经有多个案例支撑时，将其升级成 Model 文件。

---

## 11. 当前优先级

当前不要继续扩展复杂系统。

优先跑通一个低摩擦闭环：

```text
用户发碎片
↓
AI 整理
↓
用户一句话校正
↓
AI 入库
```

当前最值得优先处理的问题：

1. 结构理解 + 表达 + 系统整合在真实场景里长什么样？
2. 如何把复杂的东西讲清楚？
3. 什么是路径模式？哪些人物路径可以迁移到用户身上？
4. 如何把 AI 变成执行系统，而不是只当工具？

---

## 12. 对 Codex 的工作要求

如果 Codex 参与维护这个仓库，请遵守：

1. 不要把本仓库改造成普通资料库。
2. 不要随意新增复杂目录。
3. 不要把具体业务案例大量塞进本仓库。
4. 不要过早把问题升级成模型。
5. 所有 Model 必须能指导行动。
6. 优先减少用户手动维护负担。
7. 优先维护系统结构、模板、规则和可复用模型。
8. 如果需要新增文件，优先说明新增理由。

---

## 13. 一句话总结

这个仓库的意义不是记录更多东西，而是帮助用户把敏感捕捉到的信息，转化成可以复用、可以行动、可以反复修正的认知系统。
